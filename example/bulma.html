Bulma adapter

1416 custom properties, driven by about thirty declarations — because Bulma decomposes every colour into hue, saturation and lightness and derives the rest.

Colour families

Each of these is three numbers in the adapter. Bulma derives the hover, active, light, dark and invert variants itself by shifting lightness on the same hue.

Surfaces

A .box sits on scheme-main, which the adapter points at the surface token — while the page behind it keeps bg-page through --bulma-body-background-color. Bulma has no page/surface split of its own, so the adapter makes one using the only whole-colour variable it exposes here.

What this page is testing:
  • A library that will not take a colour. Bulma wants --bulma-primary-h/s/l, not --bulma-primary. CSS cannot take a var() apart, so the channels are computed from the theme's own colour at build time and emitted per theme — the same answer Bootstrap's --bs-primary-rgb needed, reached from a different direction.
  • Gamut mapping is load-bearing. oklch describes colours sRGB cannot show; asking for their HSL channels raw returns saturation above 100%, which CSS rejects. The adapter maps into sRGB with local-minde first, which preserves lightness and hue instead of merely clipping.
  • The honest cost. A decomposed value can follow a theme but not a runtime override. Rewriting --app-bg-action on :root moves Bootstrap, daisyUI and Pico live; it does not move Bulma's channel-derived colours. Everything Bulma exposes whole — radius, spacing, fonts, the body background — stays live and is mapped as a reference.
  • Derivability beats surface size. Bulma exposes far more variables than Bootstrap and needs a far smaller adapter, because --bulma-button-h is just var(--bulma-scheme-h). The cost of an adapter is set by how a library is organised, not by how much it ships.
