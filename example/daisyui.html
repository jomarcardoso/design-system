Contexts reach into the library

data-surface="inverted" changes a handful of layer 2 tokens. The adapter re-declares its mapping at every boundary that can move a token — :root, [data-theme] and [data-surface] — so daisyUI follows. Declaring only on :root would freeze the library at the root's theme, because a custom property is substituted where it is declared and inherits as that result.

Accent is a default, not a limit

Out of the box accent resolves to the same colour as secondary, because layer 2 models two brand roles and daisyUI wants three. That compression is the DEFAULT — it is what a two-brand-colour product wants — and it is deliberately not the ceiling.

The button below sets --app-accent-bg and --app-accent-fg on :root and nothing else. No adapter is edited, no CSS is forked, no token is emitted until you press it. If a compression could not be undone this cheaply, choosing this foundation would deliver less than using daisyUI directly — which is the one thing a universal base must never do.

--app-accent-bg is unset — accent inherits from bg-selected

Where the two adapters agree and disagree:
  • Same direction. Both are one-way — library variable reads our token, never the reverse — and both are leaves nothing depends on.
  • Same selector strategy. Both re-declare their mapping on :root, [data-theme], [data-surface] so themes and contexts propagate.
  • Different amount of work, for a reason. daisyUI keeps variants as references, so one variable moves everything. Bootstrap compiles them to literals, so its adapter re-binds per variant and also needs bootstrap-entry.scss for the build-time half.
  • Both compress where layer 2 is deliberately smaller. daisyUI wants three interactive roles and three base shades; the foundation offers two of each. The adapter maps what exists and documents the overlap rather than inventing --app-bg-accent, which would be the library's shape leaking upward.
